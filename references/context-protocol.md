# 分层上下文协议与 Token 经济

## 1. 问题模型：切换成本到底花在哪

在工具 A 的会话里，AI 的项目认知 = 对话历史中逐步积累的心智模型。
换到工具 B（或在 A 里换模型）后这份认知归零，重建成本来自四处：

| 浪费来源 | 典型表现 | 本协议对策 |
|---|---|---|
| 全仓遍历 | ls/find、逐个打开源码猜结构 | `code-index.md` 一份地图定位，只读目标文件 |
| 重复加载 | 每个工具各自维护一套规则，内容重复 N 份 | 单一事实源 + 10 行指针，规则只写一遍 |
| 长对话重发 | 换模型要带着全部历史，越滚越大 | 收工时压缩成结构化 HANDOFF，只传状态不传过程 |
| 探索弯路 | 新工具不知道试过什么不行，重踩一遍 | HANDOFF「陷阱」区沉淀失败路径 |
| 文档泛滥 | 每个需求新建一份文档，越堆越乱，分不清哪份算数 | 一个需求一份文档 + `DOCS.md` 登记索引 |
| 特性漂移 | 用户插话/追加被当成新需求重做，做出来不是用户要的 | 动手前 intake 四类证据裁定改还是建，结论写进 `Intent` |

核心思想：**把工作记忆从对话窗口外置到仓库文件**。对话是易失的、按 token 计费的；
文件是持久的、所有工具和模型共享的、只读必要片段。

## 2. 四层上下文结构

| 层 | 文件 | 性质 | 何时读 | 谁维护 |
|---|---|---|---|---|
| L0 工具指针 | CLAUDE.md、.cursor/rules 等 | 自动生成，约 10 行 | 工具启动时自己读 | sync 脚本 |
| L1 入口 | `.ai-dev/START_HERE.md` | 稳定，加载协议+文件地图 | **每个新会话必读** | 协议变化时 |
| L2 长期记忆 | project-brief / architecture / conventions / glossary / lessons / code-index | 缓慢变化 | 按需：遇到对应问题才读 | AI 随改动更新；索引脚本重建 |
| L3 工作记忆 | `.ai-dev/HANDOFF.md`（当前状态总览）+ `handoffs/`（每轮压缩流水）+ `docs/`（需求文档，一个需求一份）+ `decisions/` | 快速变化 | **每个新会话必读** | 每轮收工追加一条记录；超限归档 |

新会话固定开销只有 L1 + L3；L2 按需取；源码最后读。这与“先把整个仓库塞进上下文”
的路线相反：用一次小而确定的读取，替代一次大而盲目的扫描。

## 3. Token 预算口径

- `START_HERE.md` + `HANDOFF.md` + `handoffs/INDEX.md` 合计控制在约 1000 token 量级；
  `HANDOFF.md` 硬上限默认 120 行（由 archive_handoff.py 兜底），
  `INDEX.md` 一行一条记录，记录数硬上限默认 200 条（超出把最旧的搬进 `archive/handoffs/`）。
- `handoffs/` 单条记录保持“一屏以内”：它只服务“还原那一轮到底要做什么+结论”，过程细节不进去。
- `docs/DOCS.md` 一行一份文档，与 `handoffs/INDEX.md` 同为“换 Agent/换会话后一次读恢复现场”的入口；
  单个需求文档保持“一屏到两屏”，变长说明混进了多个主题，应拆题而不是任其膨胀。
- `code-index.md` 默认输出上限 1200 行（`--max-lines` 可调）；它只在需要定位代码时读，
  且读索引的开销远小于遍历同等文件数。
- 单个 L2 文档保持“一屏到两屏”；变长就拆到 `decisions/` 或新文件，并在 START_HERE 登记。
- 粗略换算：中文约 1 字 ≈ 1.5–2 token，英文约 1 词 ≈ 1.3 token；拿不准就数行数，
  文档类每行约 10–20 token。

## 4. 六个标准动作 SOP

### init — 首次把项目接入协议（AI 全自动，用户零命令）
1. 由 AI 运行 `scripts/init_project.py <项目目录>`（默认 detected；明确要全工具覆盖加 `--all`）。
   环境没有 Python 时走“无脚本降级”：AI 用文件工具按 SKILL.md 等价落地，不要求用户安装。
2. **脚本跑完不是结束**：AI 立即以 code-index 为地图扫描真实代码，亲自起草
   project-brief / architecture / conventions / glossary（术语表只留会被猜错的业务黑话/缩写），
   事实只来自代码与用户，不确定标“待确认”，禁止编版本号与命令；
   起草后把“仅靠代码定不了、又会改变方向”的关键问题（真实命令、术语含义、本期边界）一次性集中问用户；
   architecture 写“改什么去哪改”速查；补项目特有 ignore.conf 后重建索引。
3. 跑 `doctor.py --fix` 收尾，确认无 error；只把“待用户决策项”汇报给用户，不罗列过程。

### resume — 新会话 / 换工具 / 换模型（自动执行，不要求用户提醒）
1. 读 START_HERE → HANDOFF（L2 暂不读）。
2. 一两句话对齐现状与下一步；任务清晰直接开工，仅在有歧义或风险时请用户确认。
3. 按任务需要查 code-index 定位，再精读目标源码；不做全仓扫描。
4. 发现 HANDOFF 与代码现状矛盾时，以代码为准并当场修正 HANDOFF。

### intake — 用户提出需求时（第零原则：先受理，再动手）

用户说话是随意的：功能可能已做完、做一半，或正在被改表述；也可能做到一半插话、输出完又追加要求。
不凭措辞猜，先拿证据裁定这轮到底是**改现有文档**还是**新建**——判错的代价是特性漂移（做出来的不是用户要的）。

1. 跑 `scripts/doc_registry.py <根> --intake --user-file user.txt`（无 Python 时按同样四类证据人工核对）。
2. 证据与优先级：

| 证据 | 说明 |
|---|---|
| `handoffs/` 里未闭环的 `Next` | 最可能的"续做 / 更正"信号（相关度需过阈值，防止"导出报表"误判成"继续做登录"） |
| `specs/*/tasks.md` 未完成任务 | Spec Kit 流程里的半成品 |
| `docs/DOCS.md` 现有文档 | 需求的长期事实源 |
| 代码地图 | 兜底对照 |

优先级：**active 文档 > 未闭环记录 > specs > 全新主题**。文档是需求的长期事实源，记录只是过程流水；
有主文档就必须落到文档上，否则"改需求"会被当成"新任务"重新建一份文档——这就是特性漂移的起点。

3. 判定与动作：

| 判定 | 含义 | 动作 |
|---|---|---|
| `NEW` | 三类证据均未覆盖 | `--find` 换关键词二次确认无主，才照 `docs/0000-template.md` 新建并 `--add` 登记 |
| `EXTEND` | 扩展/修改已有功能 | 改现有文档，**禁止新建**；原话并进文档「需求变更」小节 |
| `FIX` | 修复既有行为 | 定位到规定该行为的那份文档，改它 |
| `CONTINUE` | 续做半成品 | 接着未闭环的 `Next` 干，并补一份文档把需求定下来 |
| `CORRECTION` | 更正/追加 | 并进当前需求文档，绝不另起 |

4. **文档纪律**：全部需求文档只放 `.ai-dev/docs/`，`DOCS.md` 是唯一登记索引——新建前必须先查它。
   **一个需求只对应一份文档**，按主题命名（`auth-sms-login.md`），严禁按对话轮次命名（`登录-第2次.md` 是反模式）。
   用户分几次说、中途插话、输出后追加、发现理解错了，统统是修改现有文档。
5. **裁定留痕**：结论写进本轮 handoff 记录的 `### Intent` 小节（例 `EXTEND → docs/auth-sms-login.md`），
   下一个 Agent 读得到，不会重新立项。光有 Intent 没有 Done/Next/Verify/Risks 的记录不合规，doctor 会抓。

### handoff — 收工 / 切换前（省 token 的关键动作）
按 HANDOFF 模板更新，判断每条信息去留的标准：
**“下一个模型不知道这件事，会不会走错路或重复劳动？”** 会则留，不会则删。
- 留：目标与背景一句、可验证的完成项、下一步具体动作、新形成的约束/决策、失败路径、改动文件及原因。
- 删：对话过程、情绪与寒暄、已被代码自解释的实现细节、大段代码/日志/报错原文（写路径即可）。
- 结构变动 → reindex；重大决策 → 补一条 ADR。
- **失败路径分层**：本次临时坑写 HANDOFF 陷阱区；某个坑重复出现第二次，提升到 `lessons.md`（永久教训，不随 handoff 压缩丢失）。新 AI 动手前先查 lessons.md。

#### 3.1 每轮对话压缩规范（`handoffs/`）

上下文一长就失忆，根因是“压缩”没有落到文件、也没有格式。本协议把压缩定义为**每轮对话结束必须追加一条独立记录**：

```text
1. 时间戳        ISO 8601 带时区，例 2026-10-12T16:20:33+08:00
2. Agent-会话Id  哪个 Agent、哪个会话产生的，例 claude-code / a1b2c3d4
3. 用户原话      用户这一轮的完整原始需求，一字不删、不改写、不概括
4. 本轮压缩      Done / Next / Verify / Risks 任意组合（可缺省，至少一段）
```

| 段 | 内容 |
|---|---|
| `Done` | 已经做了什么，具体到可验证结果（改了哪个文件、跑到什么状态） |
| `Next` | 下一步做什么，按依赖排序，`- [ ]` 形式，完成即勾选 |
| `Verify` | 要跑什么测试 / 命令证明 Done 成立 |
| `Risks` | 有什么坑：试过且走不通的路、容易踩的雷、要避开的事项 |
| `Intent` | 本轮 intake 受理结论（`EXTEND → docs/auth-sms-login.md`），防下一个 Agent 重新立项 |

**为什么不是全写进 `HANDOFF.md`**：单文件既会无限膨胀（token 预算失控），又会因并行 Agent 互相覆盖而丢记录。
`handoffs/` 一条记录一个文件（文件名 `<时间戳>-<Agent>-<会话Id>.md`，只增不改），
`INDEX.md` 一行一条汇总（含 Agent / 会话 / 开放 Next 计数），任何新会话读一个索引即可定位，
需要完整上下文时再按文件名读那一条。`HANDOFF.md` 仍保留为**当前状态总览**，每轮把最新结论并进去，
两者不复制内容，只做汇总。

**并发安全**：记录各自独立成文件，写方永不覆盖他人；`INDEX.md` 用“临时文件 + 原子替换”重建并加文件锁，
同秒同 Agent 同会话的第二次写入自动加序号。多 Agent 并行写同一项目不会丢记录。

**落地路径**：主控环境跑 `scripts/log_handoff.py`（`--user-file` 保原话完整，`--agent`/`--session` 显式指定身份）；
无 Python 环境照 `.ai-dev/handoffs/0000-template.md` 手工写文件并在 `INDEX.md` 补一行。

#### 3.2 多 Agent 协作约定

- 各写各的文件；先读 `INDEX.md` 的「开放 Next」列再动手，避免撞车。
- 接手别人的活：先读那条记录，再在自己记录里写明“接手自 <文件名>”。
- `HANDOFF.md` 是唯一共享黑板，冲突时以代码现状为准，并把冲突写进自己那条的 `Risks`。
- 一个会话一个 Id：同会话内复用，换会话必须换 Id，否则无法区分是谁写的。

### reindex — 增删/移动文件或模块后
运行 `scripts/build_index.py`；架构层面的变化同时改 architecture.md，
索引噪音（生成物、构建目录）写进 `.ai-dev/ignore.conf`。

### decision — 难以逆转的决定
复制 `decisions/0000-template.md` 为 `NNNN-短标题.md`，写背景/备选/决策/后果。
ADR 只记“为什么”，实现细节归代码与架构文档。

## 5. 腐化治理（上下文长期有效的维护节奏）

- **doctor 体检**：`scripts/doctor.py [--fix]` 自动发现六类腐化——必备文件缺失、L2 还是空模板、
  code-index 比源码旧（按 mtime）、HANDOFF 超限、指针缺失/漂移、`.ai-dev` 被 git 误忽略；
  退出码 0/1/2 对应健康/警告/错误。init 收尾、用户问“正常吗/检查下”、里程碑节点都跑一次。
- **对话流水腐化**：`doctor.py` 专项检查 `handoffs/`——索引与磁盘漂移（自动重建）、
  记录缺 `devctx-handoff` 标记 / 缺用户原话 / 无 Done/Next/Verify/Risks 任一节（定位到具体文件名）、
  记录数超 200 条（自动归档最旧的）、HANDOFF.md 落后于流水（提示滚动更新）。
- **文档腐化**：`doctor.py` 与 `doc_registry.py --check` 专项检查 `docs/`——未登记文档
  （绕过 `DOCS.md` 直接落盘，**错误级**，`--fix` 可自愈）、文档缺主题或缺来源需求、
  两份文档主题重复（"文档爆掉"的起点，应合并）、无任何 handoff 记录引用（来源需求不可追溯）。
- **每次 handoff 顺手检查**：HANDOFF 是否超 120 行（超了归档）、下一步是否仍可执行、
  `handoffs/INDEX.md` 与磁盘记录数是否一致、HANDOFF.md 是否落后于最新一条记录。
- **里程碑节点**：doctor 全量体检，校对版本/命令、architecture 模块表与 code-index 一致。
- **指针漂移**：工具升级后私有规则被改写，重跑 sync_rules.py；CI 用 `--check` 拦截。
- **单一事实源巡检**：发现同一规则出现在两个文件，立即合并并在原处留路径引用。
- 归档只搬 `<!-- ARCHIVE-LINE -->` 以下的历史区，脚本绝不触碰活跃状态；
  若活跃区本身超限，只能由 AI 手工压缩，脚本会明确拒绝代删。

## 5.5 主控 / 协作分工与自包含约束

- 装本技能的主控 AI 才用脚本；协作 IDE 的 AI 不装技能，只读项目内文件。
- 因此 `.ai-dev/` 与指针里所有动作都要能“无技能手工等价完成”：例如重建索引，
  START_HERE §3 同时给出“主控跑脚本”和“协作方按现有格式手工增量更新”两条路径。
- 生成的文件不得出现“运行 scripts/xxx.py”这类协作方无法满足的硬性要求（主控动作除外并注明）。

## 5.6 写给 AI 的文档原则（START_HERE / 指针 / L2 文档都适用）

本技能生成的所有文件都是"另一个 AI 经指针到达后要读的文档"，写作时遵守：
- **祈使句、可执行**：写"先读 X，再做 Y"，不写抒情或背景介绍。
- **写清何时读、何时更新**：每个文件在 START_HERE 地图里标明触发条件与更新时机。
- **单一职责**：一个文件只讲一类事；变长就拆到 decisions/ 或新文件，并在 START_HERE 登记。
- **能删则删**：AI 读文档按 token 计费，删掉代码已自解释、对话已沉淀的内容。
- **术语只用 glossary 定义过的词**：业务黑话先写进 glossary，正文直接用，不再每次解释。
- **一份内容只存一处**：复用写路径引用，不复制粘贴；发现重复立即合并。

## 5.7 与 speckit / Spec Kit 等规格驱动工具的分层配合

speckit（[github/spec-kit](https://github.com/github/spec-kit)，GitHub 官方 spec 驱动开发工具）解决"这次新需求怎么做"：constitution → specify → clarify → plan → tasks → implement，产出在 `specs/<名>/`（spec.md / plan.md / tasks.md），工具配置在 `.specify/`。本协议解决"项目长期记忆怎么跨工具/模型/人/时间保持"，产出在 `.ai-dev/`。两者**互补不内嵌**：

- **推荐安装**：`uv tool install specify-cli` 后 `specify init --here --integration <agent>`，官方版自动生成对应平台的 skill 文件。第三方打包（dceoy/speckit-agent-skills、skills.sh）默认不需要，仅在 agent 不在 spec-kit 支持列表时考虑。
- **文件分工**：`specs/<名>/` 是 speckit 的事实源（spec/plan/tasks），`.ai-dev/` 是项目长期记忆；互不复制内容，只写路径引用。
- **桥梁在 HANDOFF（自动同步）**：handoff 时 AI 自动列出 `specs/` 下未闭环的 spec，读对应 `tasks.md` 勾选项算进度（已完成 N / 共 M 条），把 `specs/<名>/tasks.md 第 N/M 条（正在做什么）` 写进 HANDOFF 元信息；换工具后新 AI 读 HANDOFF 就知道在 speckit 流程哪一步，不用重读整个 spec。
- **lessons 沉淀流程坑**：speckit 流程里踩的坑（如"不要跳过 clarify 导致 plan 返工"）重复出现第二次，提升到 `lessons.md`。
- **许可证**：spec-kit 是 MIT，本项目也是 MIT，无传染问题；独立安装，通过文件系统对接。

## 6. 反模式（明确禁止）

- 在多个工具私有文件里复制粘贴同一份项目规则。
- 新会话不读 HANDOFF 就直接改代码。
- 用 code-index 能回答的问题却批量打开源码。
- 把完整对话记录、整段日志贴进 HANDOFF。
- 让 L2 文档无限增长而不拆分、不归档。
- 未经用户确认把猜测的技术栈版本、命令写成“事实”。
- init 跑完脚本就交差，把空模板 L2 留给用户自己填。
- 让用户手动敲脚本路径/命令，或因机器没有 Python 就要求用户安装（应走无脚本降级）。
- 在项目文件里写死只有主控环境才有的脚本路径，导致协作 IDE 无法照做。
- **把每轮对话的压缩堆进单个 HANDOFF.md**（会无限膨胀）或**多个 Agent 抢写同一个文件**（互相覆盖丢记录）；
  每轮必须写独立的 `handoffs/<时间戳>-<Agent>-<会话Id>.md`。
- **压缩时概括、改写用户原话**——它是换 Agent 后还原需求的唯一依据，必须一字不删。
- 写完记录不更新 `INDEX.md`，或不读索引就动手（看不到别人还欠的活，必然撞车）。
- **每个新需求都新建一份文档**、或按对话轮次命名文档（`登录-第2次.md`）——一个需求只对应一份文档，
  按主题组织并登记进 `DOCS.md`；用户插话/追加/更正是改现有文档，不是新建。
- **不跑 intake 就凭用户措辞猜"这是新功能还是改旧功能"**——先拿四类证据裁定，
  结论写进 `Intent`；判错的代价是特性漂移，做出来的不是用户要的。
