## 1. 它解决什么问题

| 痛点 | DevCTX 的做法 |
|---|---|
| 换 IDE / 换模型后，AI 忘了项目是什么、做到哪了 | 项目认知外置为 `.ai-dev/` 一套文件，新会话自动读入口恢复现场 |
| 长会话上下文一长就"失忆" | 每轮对话结束自动压缩成一条记录，精华落盘，不靠聊天窗口记 |
| 每轮对话都重读整个代码库，浪费大量 token | 只有约 1000 token 的入口文件固定读，代码按索引按需精读 |
| 多个 Agent / 多会话同时开发，互相覆盖、撞车 | 每条记录独立成文件、索引原子重建 + 文件锁，并发安全 |
| 每个需求都新建一份文档，越堆越乱、分不清哪份算数 | 一个需求一份文档 + `DOCS.md` 登记索引，未登记即错误 |
| 用户插话 / 追加被当成新需求重做，做出来不是用户要的 | 动手前 intake 需求受理，四类证据裁定"改还是建"，结论留痕 |
| 不同工具各写各的规则，改一次要同步 N 份 | 单一事实源 + 薄指针，规则只写一遍 |
| 新工具不知道项目里哪些黑话是什么意思 | `glossary.md` 术语表统一语言，一句话定义，不再反复猜 |
| AI 干活留下 `__pycache__`、`*.tmp`、测试缓存等垃圾 | 说"收工"，自动列清单、你确认后才删 |
| 某个会话特别长、残留散布全项目 | 说"深度清理"，按该会话的完整上下文精确圈定它的残留 |

**核心承诺：用户零命令、零设置。** 你只需要表达意图（"给这个项目接入 / 接着上次做 / 收工 / 深度清理"），其余动作链由 AI 自动完成。

## 2. 核心原理（3 分钟看懂）

项目认知是易失的（只存在于对话历史里），DevCTX 把它**外置为项目内一套文件**：

```
你的项目/
├── .ai-dev/                  ← 单一事实源（随项目走，git 提交后全员共享）
│   ├── START_HERE.md         ← L1 入口：新会话第一件事读它（含加载协议 + 文件地图 + 需求受理）
│   ├── HANDOFF.md            ← L3 工作记忆：当前状态总览（滚动更新，共享黑板）
│   ├── handoffs/             ← 每轮对话压缩流水（一条记录一个文件，只增不改）
│   │   ├── INDEX.md          ← 流水索引，一行一条，换会话读它就恢复现场
│   │   └── 20261012-214500-claude-code-a1b2c3d4.md   ← 单轮记录（时间戳-Agent-会话Id）
│   ├── docs/                 ← 需求文档（一个需求一份，按主题组织）
│   │   ├── DOCS.md           ← 文档登记索引（唯一事实源，未登记即错误）
│   │   └── auth-sms-login.md ← 某需求的唯一文档（含需求原文/变更/结论/待办）
│   ├── project-brief.md      ← L2 长期记忆：项目定位、技术栈、运行命令
│   ├── architecture.md       ← L2：模块分区、"改什么去哪改"
│   ├── conventions.md        ← L2：编码/命名/提交规范
│   ├── glossary.md           ← L2：项目术语表（黑话字典，统一所有工具的语言）
│   ├── lessons.md            ← L2：永久教训（踩过的坑，重复出现第二次提升到这）
│   ├── code-index.md         ← 代码地图（文件路径 + 一句话职责 + 行数）
│   ├── ignore.conf           ← 代码索引忽略规则
│   ├── decisions/            ← ADR 架构决策记录（一决策一文件）
│   └── archive/              ← 过期 HANDOFF / 对话记录 / 需求文档归档
├── CLAUDE.md / AGENTS.md / .cursor/rules/...   ← 薄指针（各工具的规则文件，
│                                                  只写"去读 .ai-dev/"，十几行）
```

**四层上下文模型：**

| 层 | 文件 | 何时读 | 谁维护 |
|---|---|---|---|
| L0 工具指针 | `CLAUDE.md`、`AGENTS.md`、`.cursor/rules/…`、`.trae/rules/…` 等 | 工具启动时自动读（十几行） | sync 脚本自动生成 |
| L1 入口 | `.ai-dev/START_HERE.md` | **每个新会话必读** | 协议变化时 |
| L2 长期记忆 | project-brief / architecture / conventions / glossary / lessons / code-index | **按需读**（遇到对应问题才读） | AI 随改动更新 |
| L3 工作记忆 | HANDOFF.md + handoffs/ + docs/ + decisions/ | **每个新会话必读** | 每轮自动追加 |

**工作流：**

```
新会话 → 读 START_HERE + HANDOFF + INDEX（~1000 token）→ 自动恢复现场
动手前 → 需求受理（查有没有人正在做 / 有没有现成文档，防做重、防漂移）
每轮结束 → 自动追加一条压缩记录 + 滚动更新 HANDOFF
```

## 3. 安装

DevCTX 是一个 **AI 技能（Skill）**，装在你使用的 AI 工具/IDE 里。**每个工具都装，才能实现跨工具无缝**——你在哪个软件开发，哪个软件就认识 `.ai-dev/`。

### 3.1 三步安装（零配置）

| 步骤 | 做什么 |
|---|---|
| **第 1 步** | 获取整个文件夹：GitHub 仓库页 `Code → Download ZIP` 解压得到 `devctx/`（或 `git clone`）。**必须是整个文件夹**（含 SKILL.md + scripts/ + assets/ + references/，缺 scripts 里的 .py 就无法自动干活） |
| **第 2 步** | 把 `devctx/` 文件夹放进 AI 助手的"技能目录"（豆包桌面端 `.user_skills/devctx/`；其他支持 skills/rules 的助手按其文档放置） |
| **第 3 步** | 在项目里对 AI 说一句："给这个项目接入统一上下文" |

### 3.2 各工具怎么装

| 工具 | 安装方式 |
|---|---|
| 豆包 / 豆包工作台 | 把 `devctx` 技能目录放进技能安装位置，对话里选中该技能 |
| Cursor | 技能装到 Cursor 的规则/技能目录；项目内由 `.cursor/rules/ai-dev-context.mdc` 指针自动引导 |
| Claude Code | 安装 skill 后，项目内 `CLAUDE.md` 指针自动引导 |
| Trae / Trae Work CN | 技能装到 Trae；项目内 `.trae/rules/ai-dev-context.md` 指针自动引导 |
| Windsurf / Copilot / Cline / Roo / Gemini / Codex / Aider 等 | 同上：装技能 + 项目内自动生成对应指针文件 |

> **关键点**：指针文件（`CLAUDE.md`、`AGENTS.md`、`.cursorrules` 等）是 devctx 自动生成的薄指针，只有十几行，**规则绝不复制多份**。项目内自包含，即使没有装技能的 AI 也能靠指针 + `.ai-dev/` 正常运转。新增工具只需在 `scripts/_common.py` 的 `TOOL_SPECS` 加一条映射。

### 3.3 需要装 Python 吗？

**不需要用户安装。** 脚本用纯 Python 标准库编写，由 AI 调用；如果机器上没有 Python，AI 会走"无 Python 降级路径"，用文件工具手工完成等价结果（见 §22）。

## 4. 第一次接入项目（init）

对 AI 说一句：

> **"给这个项目接入 devctx"** 或 **"我要在多个 IDE 之间切换开发这个项目，统一一下"**

AI 会自动完成：

1. 创建 `.ai-dev/` 全套上下文文件（入口 / 交接 / 长期记忆 / 代码地图 / 决策记录 / 归档）；
2. **自动检测技术栈**：Node / Python / Go / Rust、monorepo 子包（packages/apps/services）、.env 环境变量、部署方式（Docker / CI），自动预填项目简报；
3. 生成首份代码地图 `code-index.md`；
4. 扫描代码里的 TODO / FIXME / 半成品，**自动把项目现状 spec 化**（已完成的写 spec、未完成的走 spec → plan → tasks）；
5. 给在用的每个工具生成指针文件；
6. **AI 亲自起草 L2 文档**（不是留空模板）：项目简报、架构（含"改什么去哪改"速查）、规范、**术语表**、教训——事实只来自代码与用户，不确定标"待确认"，禁止编造版本/命令；
7. 把"仅靠代码定不了、会影响方向"的问题（真实运行命令、业务术语含义、本期边界）**一次性集中**问你，不逐条打断；
8. 跑体检确认全绿，然后告诉你一句话：**"已接入，以后直接提需求；换其他 IDE 新开会话即自动接续"**。

## 5. 存量项目接入（retrofit）

适用：**项目已经被多个 Agent / 多会话开发过**（代码是攒的、文档散落、半成品看不见）。直接 init 只会得到一套空壳。

对 AI 说：

> **"这个项目之前被好几个 AI 开发过，帮我接入 devctx"**

AI 自动完成：

| 阶段 | 做什么 |
|---|---|
| **scan 证据清点** | 按"作者 × 时间窗"（间隔超 14 天自动分窗）把 git 历史切成**历史会话画像**（`legacy-bob`、`legacy-alice-2`…），并列存量文档清单与 TODO/FIXME 半成品信号 |
| **probe 会话探测** | 探找你本机各工具的本地会话存储（Claude Code / Cursor / Windsurf / Trae / Cline / Roo / Gemini 等），**只列 Id / 路径 / 数量，绝不读消息正文**；有真实会话 Id 可精确回填，没有也不阻塞 |
| **baseline 会话回填** | 每个历史画像回填一条**基线重建记录**（agent 固定 retrofit）——"压缩各会话 Id"：INDEX 从此列出"legacy-bob 欠着验证码网关没接完"；历史口述同样回填，记不得写"历史口述：…"，**禁止编造** |
| **consolidate 文档归并** | 对每份存量 .md 给"并入哪份需求文档 / 独立成篇"建议（**匹配看正文**，标题常常不含主题词）；AI 合并进 `.ai-dev/docs/`（不复制两份，原处留路径引用）后登记（source 记 RETROFIT） |

两条纪律：**历史口述同样回填，记不得就写"历史口述：…"，禁止编造**；**存量文档合并不复制两份**，原处留路径引用。半成品信号（TODO/FIXME）就是接入后第一批「开放 Next」。

## 6. 日常使用

接入之后，**什么都不用改变**，正常提需求即可：

| 你说 | AI 自动做 |
|---|---|
| "接着上次做登录" | 读 HANDOFF + 索引，沿"下一步"继续 |
| "把 X 改成 Y" | 动手前先需求受理（查有没有主文档 / 有没有人正在做），再改 |
| （什么都不说，直接开新会话） | 自动恢复现场 |
| "上次用 Cursor 那个会话干了什么" | 按会话 Id / 时间戳找回当时记录（见 §21） |
| "检查一下项目" | 跑 doctor 体检（见 §15） |

## 7. 每轮对话压缩规范（handoff）

**每轮对话结束（AI 输出回复后）自动执行**，这是"换 Agent 不丢上下文"的核心机制。每条记录固定结构：

```
1. 时间戳        ISO 8601 带时区，例 2026-10-26T16:20:33+08:00
2. Agent-会话Id  哪个 Agent、哪个会话产生的，例 claude-code / a1b2c3d4
3. 用户原话      你这一轮的完整原始需求，一字不删
4. 本轮压缩      Done / Next / Verify / Risks 任意组合（至少一段）
```

| 段 | 写什么 |
|---|---|
| **Done** | 已经做了什么，具体到可验证结果（改了哪个文件、跑到什么状态） |
| **Next** | 下一步做什么，按依赖排序，用 `- [ ]`，完成即勾选 |
| **Verify** | 要跑什么测试 / 命令来证明 Done 真的成立 |
| **Risks** | 有什么坑：试过且走不通的路、容易踩的雷、要避开的 |
| **Intent** | （需要时）本轮需求受理结论，如 `EXTEND → docs/auth-sms-login.md`，防下一个 Agent 重新立项 |

**为什么不全写进一个文件**：单个 `HANDOFF.md` 会无限膨胀（token 预算失控），且并行 Agent 会互相覆盖丢记录。所以：
- 每轮写**独立小文件**进 `.ai-dev/handoffs/`，文件名 `<时间戳>-<Agent>-<会话Id>.md`，**只增不改**；
- `INDEX.md` 一行一条自动汇总（含 Agent / 会话 / 开放 Next 计数），任何新会话读一个索引即可定位，需要完整上下文再按文件名读那一条；
- `HANDOFF.md` 仍保留为**当前状态总览**，每轮把最新结论并进去（两者不复制内容，只做汇总）。

**你的确认方式**：AI 每次追加成功后，会在回复末尾附一句 `记忆已储存（<记录文件名>）`。看到这句 = 本轮上下文已压缩落盘。写入失败会如实报告，不会假装储存。

## 8. 防文档漂移（intake 需求受理）

**这是本项目最核心的防错机制之一**：用户随口说的话不能直接当需求——功能可能已做完、做一半、或正被改写；用户会中途插话、输出完又补要求。**照字面新开文档/任务，做出来的东西就会漂移，甚至根本不是用户要的。**

所以每次接到需求、每次要写文档前，AI 必须先做**需求受理（intake）**：

### 8.1 四类证据

| 证据 | 说明 |
|---|---|
| `handoffs/INDEX.md` 里未闭环的 `Next` | 有没有人正在做这件事 |
| `specs/*/tasks.md` 未完成任务 | Spec Kit 流程里排着没做完的任务 |
| `docs/DOCS.md` 文档索引 | 这个需求有没有主文档 |
| `code-index.md` 代码地图 | 代码里是不是已经有了 |

### 8.2 五种裁定

| 判定 | 含义 | AI 的动作 |
|---|---|---|
| `EXTEND` | 已有 active 文档覆盖该主题 | **改那份文档**（在「需求变更」追加本次原话），禁止新建 |
| `CONTINUE` | 有未闭环记录但还没文档 | 接着做，并补一份文档把需求定下来 |
| `NEW` | 三类证据都没有 | 先换关键词二次确认无主，才建 `docs/<领域>-<主题>.md` 并登记 |
| `FIX` | 修复既有行为 | 定位到规定该行为的那份文档，改它 |
| `CORRECTION` | 用户否定 / 更正刚才的做法 | 并进当前那份需求文档，绝不另起 |

**裁定优先级：active 文档 > 未闭环记录 > specs > 全新主题。** 文档是需求的长期事实源，记录只是过程流水——有主文档就必须落到文档上，否则"改需求"会被当成"新任务"重新建一份文档，那就是特性漂移的起点。

### 8.3 裁定留痕（Intent）

判定结论必须写进本轮 handoff 记录的 `### Intent` 小节（例 `EXTEND → docs/auth-sms-login.md`）——下一个 Agent 读得到，不会重新立案。没有 Intent 的记录 doctor 会抓。

### 8.4 典型场景

```text
用户："短信验证码登录先别用手机号了，改用邮箱"   ← 做到一半插话
intake → EXTEND → docs/auth-sms-login.md        ← 改同一份，禁止新建
```

**你只需要正常说话**（包括插话、追加、更正），AI 会自动把它并进正确的那份文档。

## 9. 文档治理（一个需求一份文档）

与 intake 配套的第二道闸门：

- **一个需求只对应一份文档**，按主题命名（`auth-sms-login.md`），**严禁按对话轮次命名**（`登录-第2次.md` 是反模式，doctor 会报重复主题）；
- 全部需求文档只放 `.ai-dev/docs/`，**`DOCS.md` 是唯一登记索引**（主题 / 状态 / 来源需求 / 最近更新 / 关联记录数）——新建任何文档前必须先查它，能并进现有文档的禁止新建；
- 用户分几次说、中途插话、输出后追加、发现理解错了要更正——**统统是修改现有文档**，不是新建；
- 文档只记"这个需求定成什么样、现状如何"，**不记过程**（过程在 `handoffs/`，活跃状态在 `HANDOFF.md`）；
- 文档超过两屏 → 拆成同主题子文档并互相引用，仍然一个需求一条线；
- 已闭环 → 状态改 `stable`；确认废弃 → 归档，不堆在目录里。

**每份需求文档的固定结构**（`docs/0000-template.md` 模板）：

| 小节 | 内容 |
|---|---|
| 头部字段表 | 主题 / 状态（active/stable/archived）/ 来源需求 / 创建时间 / 最近更新 / 关联对话记录 |
| 需求原文 | 用户**第一次**提出的完整原话，一字不删 |
| 需求变更 | 插话 / 追加 / 更正，按时间正序，注明来自哪条对话记录 |
| 当前结论 | 已定稿的事实（做什么、不做什么） |
| 已废弃 / 走过的弯路 | 试过且不做的方案与原因，避免后续 Agent 重新捡起来 |
| 待办 | 未闭环项，与 handoffs 的 Next 保持一致，完成即勾选 |

**未登记文档是错误级腐化**（绕过 DOCS.md 直接落盘），`doctor --check` 可直接进 CI 拦截。

---

## 10. 术语表（glossary）

项目里不同工具、不同人会说出不同的黑话（业务缩写、专有名词、内部代号）。devctx 用 **`glossary.md` 术语表**统一语言：

- **结构**（三张表）：
  - **业务术语**：术语/缩写 + 一句话定义 + 常见误用（不要写成什么）
  - **代码与架构名词**：术语 + 定义 + 对应文件/模块
  - **外部系统与第三方**：名称 + 是什么/怎么对接 + 凭据/配置位置
- **原则**：保持精简（一屏以内），**只留"换个工具的 AI 不查就会猜错"的词**；通用技术词（如 HTTP、API）不写；凭据类条目只写配置位置，不写密钥内容；
- **什么时候用**：新会话遇到不懂的业务黑话 → 读 glossary；出现新术语或含义变化 → 更新 glossary；
- **规则**：项目正文（文档、代码命名、HANDOFF）只使用 glossary 定义过的词，业务黑话先写进术语表再直接用，不再每次解释——跨工具说同一种语言、省 token；
- **init 时自动起草**：AI 接入项目时扫描代码与需求，把会猜错的业务黑话/缩写提炼进术语表（只留会被猜错的，不写废话）。

---

## 11. 代码地图（code-index）

`code-index.md` 是项目的**代码地图**：每个源码文件一行（相对路径 + 一句话职责 + 行数）。

- **作用**：AI 定位代码先查地图，只精读目标文件，**不做全仓扫描**——这是省 token 的关键之一；
- **生成**：init 时自动生成；之后增删/移动源码文件时 AI 自动重建（`build_index.py`，默认输出上限 1200 行可调）；
- **忽略规则**：尊重 `.gitignore` 与 `.ai-dev/ignore.conf`（构建产物、生成物目录写进 ignore.conf，索引不制造噪音；凭据/密钥目录必须忽略且内容不外传）；
- **纪律**：code-index 能回答的问题，AI 不许全仓遍历或批量打开源码。

---

## 12. 永久教训（lessons）

`lessons.md` 是项目的**永久教训本**（"这个项目永远不能这么干"）：

- **临时坑** → 写进 HANDOFF 陷阱区（易失，随压缩流转）；
- 某个坑**重复出现第二次** → **提升到 lessons.md**（持久，跨阶段生效，不随压缩丢失）；
- 新 Agent 动手前先查 lessons.md，避免重蹈覆辙；
- 结构：三张表（架构与边界 / 工具链与环境 / 数据与外部系统）；
- init 时初始可为空，后续 AI 自动沉淀。

---

## 13. 架构决策记录（ADR）

难以逆转的选型/架构决定，记进 `.ai-dev/decisions/`：

- 一决策一文件：`NNNN-短标题.md`（如 `0003-短信网关选型.md`）；
- 内容：背景 / 备选方案 / 决策 / 后果——**只记"为什么"**，实现细节归代码与架构文档；
- 编号撞号会被 doctor 报**错误级**（两份 ADR 顶同一个编号 = 两份"权威"，选型失据）。

---

## 14. 自动归档（archive）

上下文不会无限膨胀：

- `HANDOFF.md` 超过约 120 行 → 把「归档线」以下历史移入 `archive/`，活跃区只压缩不删除；
- `handoffs/` 记录数超过约 200 条 → 把最旧的搬进 `archive/handoffs/`，**活跃窗口不动**；
- 需求文档已闭环 → 状态改 `stable`；确认废弃 → 归档，不堆在目录里；
- 归档只搬归档线以下的历史区，脚本绝不触碰活跃状态；活跃区本身超限时脚本拒绝代删，由 AI 手工压缩。

---

## 15. 健康体检（doctor）

对 AI 说：

> **"检查一下项目 / 正常吗"**

AI 跑 `doctor.py` 全身体检（0 健康 / 1 警告 / 2 错误），自动发现并（`--fix` 时）修复：

| 检查类 | 检查什么 |
|---|---|
| 基础文件 | `.ai-dev/` 必备文件缺失、L2 文档还是空模板（没起草） |
| 代码索引 | code-index 比源码旧（按 mtime） |
| HANDOFF | 超过 120 行、HANDOFF.md 落后于流水 |
| 指针 | 工具指针缺失/漂移、**本机在用工具缺专属指针**（探测到你在用某工具但项目没有它的指针 → 它的新会话读不到上下文） |
| git | `.ai-dev` 被误加进 .gitignore |
| 对话流水 | 索引与磁盘漂移、记录缺标记/缺用户原话/无压缩节、记录数超 200 条 |
| 文档治理 | **未登记文档（错误级）**、文档缺主题/缺来源、两份文档主题重复、无记录引用 |
| 决策记录 | ADR 编号撞号（错误级）、文件名不合规 |
| schema | 老项目没有版本标记 |

init 收尾、用户问"正常吗"、里程碑节点都会跑；`--check` 可进 CI 防漂移。

## 16. 收工清理（cleanup）

对 AI 说：

> **"收工"** 或 **"清理一下"**

AI 自动：

1. 按**明文规格**扫描项目里的 AI 残留：
   - **缓存类**（可再生，建议删）：`__pycache__` / `.pytest_cache` / `.mypy_cache` / `.ruff_cache` / `.eslintcache` / `.parcel-cache` / `.turbo` / `.vite` / `*.pyc` / `*.tsbuildinfo` / `.coverage` 等；
   - **临时文件类**：`*.tmp` / `*.temp` / `*.orig` / `*.rej` / `*.swp` / `.DS_Store` / `Thumbs.db` 等；
   - **谨慎类**（仅列出，需明确同意才删）：`node_modules/.cache` / `.next/cache` / `.nuxt` / `.tox` / 大于 1MB 的日志；
2. **把清单完整展示给你**（数量、大小、每项说明），问"删除这些吗？"；
3. **你同意后**才删除（AI 绝不在未经同意时删）；
4. 清理结果写进本轮 handoff 的 Done，并顺手重建索引（删掉的缓存不应留在 code-index）。

**安全硬边界（永不扫描、永不删除）**：`.git` / `.ai-dev/` / `specs/` / `.specify/` / `node_modules` / `venv` / `.env` / `dist` / `build` / `coverage` / `.gradle` / `.idea`——它们不是无用文件。符号链接只删链接本身；候选 resolve 后必须仍在项目根内。

**追问缓存来源**：`--context N` 会从最近 N 轮 handoff 压缩记录里提取 Verify/Done/Risks 片段，回答"这些缓存是不是这轮测试产生的"。

## 17. 深度清理（deep cleanup，v0.7.0）

适用场景：**某个会话特别特别长**，残留散布整个项目，普通清理分不清哪些是这个会话产生的。

对 AI 说：

> **"深度清理"**（配合会话 Id，或让 AI 列出会话供选择）

AI 自动：

1. **读取该会话的全部 handoff 记录**（不是最近几轮，是全部），从 Done/Verify/Risks/用户原话中提取干活路径线索；
2. 按两条规则圈定这个会话产生的残留：
   - 候选的**完整路径**出现在该会话某条记录里 → 命中（精确，如记录写了 `scratch_a.tmp` 只圈它自己）；
   - 候选的**文件名/目录名**在该会话记录里显式出现过（如"跑 pytest 生成了 .pytest_cache"）→ 命中；
   - 记录里提过的**后缀只作提示、不圈定**（避免误伤其他会话的 `.tmp` 等）；
3. 展示圈定清单（含：该会话上下文记录数、圈定线索、提及后缀、全项目扫描数 vs 按会话圈定数），**你确认后**才删除；
4. 其他会话的缓存 / 临时文件一律不碰；安全边界与普通清理完全相同。

> 忘了会话 Id？说"深度清理"即可，AI 会从索引列出出现过会话 Id 供选择。

## 18. 多 Agent 并发协作

多个 Agent / 多个会话同时改一个项目，靠四条约定避免互相踩：

- **各写各的文件**：每条记录一个文件，文件名带 Agent 与会话 Id，永不覆盖别人的记录；`INDEX.md` 用"临时文件 + 原子替换"重建并加文件锁，并发写不丢记录；
- **先读索引再动手**：`INDEX.md` 的「开放 Next」列列出**任何 Agent 还欠的活**——包括别人的；要接手别人的活，先读那条记录拿完整上下文，再在自己记录里写明"接手自 \<文件名\>"；
- **`HANDOFF.md` 是共享黑板**：唯一被所有人滚动更新的文件；冲突时以代码现状为准，并把冲突写进自己那条记录的 Risks；
- **一个会话一个 Id**：同会话内复用，换会话必须换 Id，否则无法区分是谁写的。

## 19. 换工具 / 换会话 / 换 Agent（resume）

1. 在新工具里开新会话（装了技能的选上 devctx）；
2. AI 自动读 `START_HERE.md` + `HANDOFF.md` + `handoffs/INDEX.md`；
3. 看到 HANDOFF 里的"下一步"和 INDEX 的"开放 Next"，自动接着干；
4. 一两句话向你确认现状，不打断、不重复读代码；
5. 文档与代码矛盾时以代码为准，并当场回写修正文档。

**省 token 的原理**：固定只读入口（约 1000 token），L2 文档和源码按索引按需精读；每轮只追加压缩记录，不整体重写。

## 20. 规格驱动开发联动（Spec Kit）

对 AI 说：

> **"用 spec 做 XXX"** 或 **"用 SDD / speckit 做 XXX"**

AI 自动跑完整流程：

| 阶段 | AI 做什么 | 产物 |
|---|---|---|
| spec | 提炼短名，写用户场景（P1/P2/P3 + Given/When/Then）、功能需求、成功指标 | `specs/<NNN-短名>/spec.md` |
| plan | 写技术方案、架构决策、实施步骤、验证方式 | `specs/<NNN-短名>/plan.md` |
| tasks | 拆任务清单：依赖、并行标记、TDD 验收标准 | `specs/<NNN-短名>/tasks.md` |
| implement | 按 tasks.md 依赖顺序执行，每完成一个勾 `[x]` | 代码 + 勾选 tasks.md |

**你只需要装 devctx 一个技能**，不需要单独装 spec-kit，也不强制装 specify CLI（没有 CLI 时 AI 直接手写，功能一样）。

**收工自动同步进度**：handoff 时 AI 自动读 `tasks.md` 勾选数，把"第 N/M 条（正在做什么）"写进 HANDOFF 元信息——换工具后新 AI 一看就知道在 spec 流程哪一步，不用重读整个 spec。

**文件分工**：`specs/<名>/` 归 spec 流程（spec/plan/tasks），`.ai-dev/` 归项目长期记忆，互不复制内容，只写路径引用。

## 21. 历史回忆与时间线缺口（--find / --gaps）

记录文件名就是 `<时间戳>-<Agent>-<会话Id>.md`，`INDEX.md` 一行一条汇总——回忆路径：

| 你说 | AI 自动做 |
|---|---|
| "上次用 Cursor 那个会话干了什么" / "我们哪天改的登录逻辑" | `--find <会话Id或Agent名>` 定位条目，读 `handoffs/<该条>.md` 全文 |
| "哪里没了记忆？" | `--gaps` 列出相邻记录间隔超阈值的无记录区间（间隔大不等于漏写，那段时间可能真的没开发）；确认要补则按口述/git 回填，禁止编造 |
| "最近几轮在干嘛" | `--tail N` 读最近 N 条全文 |

## 22. 无 Python 也能用（降级路径）

机器上没有 Python 时，**AI 不会要求你安装**，而是用文件工具手工完成等价结果：

- 复制 `assets/templates/` 下模板为 `.ai-dev/` 同名文件；
- 按 `_common.py` 的 TOOL_SPECS 手工写指针文件（POINTER_BODY 同等内容）；
- 手工生成代码地图（目录树 + 每文件"路径（约 N 行）— 一句话职责"）；
- 后续 reindex / archive 手工增量完成，并在 HANDOFF 注明"本项目由无脚本路径初始化"。

## 23. Token 经济（省 token 的原理）

1. **固定开销极小**：新会话只读 START_HERE + HANDOFF + INDEX（约 1000 token），L2 与源码按需、按索引读；
2. **分层加载**：L1 入口与 L3 交接必读，L2 规范/索引按需读，源码最后读且只读目标文件；
3. **一份内容只存一处**：同一规则不复制到多个文件，复用写路径引用；
4. **增量更新**：只改变化的小节，不整体重写未变动文档；
5. **有上限**：HANDOFF 120 行、handoffs 200 条、code-index 1200 行、文档两屏——超限自动归档/拆题；
6. **每轮只追加**：压缩记录一条一个小文件，只增不改，不重复计费。

## 25. 常见问题 FAQ

**Q1：每次新对话都会浪费 token 吗？**
不会。固定只读入口约 1000 token；L2 文档、代码全部按需精读。比每轮重读整个项目省得多。

**Q2：AI 每轮都写记录，会不会很占空间？**
一条记录一个小文件，只增不改；超过约 200 条自动归档最旧的进 `archive/handoffs/`，活跃窗口不动。

**Q3：我不装技能，别人能读到我项目的上下文吗？**
能。`.ai-dev/` 项目内自包含，指针文件引导任何 AI 读它；装了技能只是让"自动执行"更顺（自动写记录、自动清理等）。

**Q4：`.ai-dev/` 要提交到 git 吗？**
要。随项目提交，团队 / 多机器才能共享上下文。doctor 会检查 `.ai-dev/` 是否被误加进 .gitignore。

**Q5：装技能需要 Python 吗？**
不需要。AI 调用脚本；无 Python 时走降级路径，等价落地。

**Q6：删除残留安全吗？**
安全。默认只列不删；删除前必须展示清单、你同意才执行；`.git` / `.ai-dev` / `dist` / `build` 等硬排除永不触碰；符号链接只删链接本身。

**Q7：换到没装技能的 IDE 会怎样？**
该 IDE 的 AI 至少会读到指针（如 `AGENTS.md` / `CLAUDE.md`）并跟着去读 `.ai-dev/`，能恢复现场、能接着干活；只是不自动写记录——换回装了技能的 IDE 继续无缝。

**Q8：我插话 / 追加要求，AI 会不会当成新需求重做？**
不会。devctx 的 intake 需求受理会在动手前查证据（有没有主文档、有没有人正在做），把你的话并进正确的那份文档；裁定结论写进 Intent 留痕，换任何 Agent 都不会重新立项。

**Q9：项目里的黑话（缩写/内部代号）AI 能看懂吗？**
能。`glossary.md` 术语表一句话定义所有会猜错的词，新会话遇到不懂的先查它；命名与文档统一用术语表词汇。

**Q10：深度清理会误删其他会话的东西吗？**
不会。它只读你指定的那个会话的全部记录，按"完整路径命中 / 名字显式提及"圈定，记录提过的后缀只提示不圈定；其他会话的缓存/临时文件一律不碰。
