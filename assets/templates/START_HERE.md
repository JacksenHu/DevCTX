# START HERE — 项目统一上下文入口

<!-- devctx-schema: v2 -->

> **给项目成员/用户**：本目录由 AI 自动维护，您平时无需打开或编辑；直接对 AI 提需求即可。
> **给所有 AI 工具/模型**：本文件是项目唯一的上下文入口（Cursor、Claude Code、Windsurf、Trae、
> Copilot、Cline、豆包、Codex 等通用）。新会话先读完本文件与 `HANDOFF.md` 再行动；
> 项目规则只维护在 `.ai-dev/` 这一份，工具私有规则文件只是指向这里的"指针"。
> 本目录自包含：即使你的环境里没有 devctx 技能，也必须按本文件协议完成全部动作。

## 1. 新会话加载协议（Resume，自动执行，不要求用户重复指令）

1. 读本文件 → `HANDOFF.md` → `handoffs/INDEX.md`（对话流水索引），沿 HANDOFF「下一步动作」继续。
   `INDEX.md` 一行一条记录，「开放 Next」列是**任何 Agent 还欠的活**——包括别人的，
   动手前先扫一眼，避免和并行会话撞车。
2. 需要某一轮的完整上下文（当时的用户原话 + 当时的压缩）时，按索引里的文件名读
   `handoffs/<该条>.md`；有 devctx 技能时也可用 `scripts/log_handoff.py --tail N` 读最近 N 条。
3. 用一两句话说明你理解的现状与接下来动作即可；任务清晰就直接开工，只在有歧义或风险时请用户确认。
4. 之后**按需**加载，不要预读：
   - 不知道项目是什么 / 怎么跑 → `project-brief.md`
   - 不知道某块代码在哪 → 先查 `code-index.md`（代码地图），再精读目标文件
   - 不确定写法/命名/提交规范 → `conventions.md`
   - 不清楚架构原因与依赖 → `architecture.md`
   - 遇到不懂的业务黑话 / 缩写 / 专有名词 → `glossary.md`（术语表）
   - 动手前先查有没有"这个项目永远不能这么干"的坑 → `lessons.md`（永久教训）
   - 项目里有 `specs/`（用了 speckit / Spec Kit）→ 按 HANDOFF「进行中的 spec」字段读对应 tasks 片段
   - "以前为什么这么定" → `decisions/` 决策记录
5. `code-index.md` 能回答的问题，不许全仓遍历或批量打开源码。
6. 文档与代码矛盾时以代码为准，并当场回写修正对应文档。

## 1.5 需求受理（接到任何需求、写任何文档之前，必做）

**用户随口说的话不能直接当需求。** 功能可能已经做完、做一半，或正被改写；
用户会中途插话、会在你输出完之后又补要求。照着字面新开一份文档/任务，做出来就会漂移。
所以动手前先受理，**按证据判定，不猜**：

```text
查 handoffs/INDEX.md 的「开放 Next」  → 有没有人正在做这件事
查 specs/*/tasks.md 未闭环项          → 有没有排着没做完的任务
查 docs/DOCS.md 文档索引              → 这个需求有没有主文档
查 code-index.md                      → 代码里是不是已经有了
```

| 判定 | 动作 |
|---|---|
| `EXTEND` | 已有 active 文档 → **改那份文档**（在「需求变更」追加本次原话），禁止新建 |
| `CONTINUE` | 有未闭环记录但没文档 → 接着做，并补一份文档把需求定下来 |
| `NEW` | 三类证据都没有 → 先换关键词再查一次，才建 `docs/<领域>-<主题>.md` 并登记 |
| `FIX` / `CORRECTION` | 修复或更正 → 落到规定该行为的那份文档，绝不新建 |

有 devctx 技能时跑 `scripts/doc_registry.py <根> --intake --user-file <原话>` 自动出判定；
没有技能时按上表手工查这四处。**判定结论必须写进本轮 handoff 记录的 `### Intent`**，
否则下一个 Agent 会重新建一份文档，漂移从此开始。

**文档纪律**：一个需求只对应一份文档，按主题命名（`auth-sms-login.md`），
**严禁按对话轮次命名**（`登录-第2次.md` 是反模式）。
用户插话 / 追加 / 更正 / "不对，应该…" → 全部并进现有文档的「需求变更」，**绝不新建**。

## 2. 文件地图（单一事实源）

| 文件 | 内容 | 何时更新 |
|---|---|---|
| `HANDOFF.md` | **活跃工作记忆**：当前任务、进度、下一步、陷阱、本次改动 | 每次收工/切换工具/切换模型时自动更新 |
| `handoffs/INDEX.md` | **对话流水索引**：一行一条，自动生成，含 Agent/会话/开放Next | 每条记录写入后由脚本自动重建 |
| `handoffs/<时间戳>-<Agent>-<会话Id>.md` | **单轮压缩记录**：时间戳 + Agent-会话Id + 用户原话 + Done/Next/Verify/Risks/Intent | **每轮对话结束都必须追加一条**，只增不改 |
| `handoffs/0000-template.md` | 单轮压缩记录的格式模板 | 协议变化时 |
| `docs/DOCS.md` | **需求文档索引**（单一事实源）：主题/状态/来源需求/最近更新 | 新建、登记、归档文档时 |
| `docs/<领域>-<主题>.md` | **一份需求一份文档**：需求原文 + 需求变更 + 当前结论 + 待办 | 该需求有任何变化时（含用户插话/追加/更正） |
| `docs/0000-template.md` | 需求文档的格式模板 | 协议变化时 |
| `project-brief.md` | 项目定位、技术栈版本、运行/构建/部署命令、环境依赖 | 技术栈或命令变化时 |
| `architecture.md` | 架构、模块职责、数据流，"改需求去哪改"速查 | 新增/删除模块或架构调整时 |
| `conventions.md` | 编码、命名、提交、测试、兼容等硬性约定与禁止事项 | 团队约定变化时 |
| `glossary.md` | 项目术语表（业务黑话/缩写=一句话定义），统一所有工具的语言 | 出现新术语或术语含义变化时 |
| `lessons.md` | 永久教训：反复踩过、跨阶段仍有效的坑（"这个项目永远不能这么干"） | HANDOFF 陷阱区某坑重复出现第二次时提升到这里 |
| `code-index.md` | 代码地图（文件 + 一句话职责 + 行数） | 增删/移动源码文件后（更新方式见 §4） |
| `decisions/` | 重大决策记录 ADR，一决策一文件 | 做出难以逆转的决定时 |
| `archive/` | 过期 HANDOFF、对话记录与需求文档归档 | 自动或手工归档时 |
| `ignore.conf` | 代码索引忽略的 glob 规则 | 索引噪音大时 |
| `specs/`（如存在） | speckit / Spec Kit 产出（spec.md / plan.md / tasks.md），不归本目录维护 | speckit 流程自行更新；handoff 时 AI 自动算进度并写进 HANDOFF |

## 3. 收工协议（Handoff，**每轮对话结束自动执行**）

> 这是多会话并发、换 Agent 不丢上下文的关键：每轮对话输出后都压缩，不等大任务完成。
> 单个 `HANDOFF.md` 装不下"每轮都写"（会无限膨胀），并行 Agent 还会互相覆盖，
> 所以每轮写**独立小文件**进 `handoffs/`，由 `INDEX.md` 汇总。

### 3.1 每轮必做：往 `handoffs/` 追加一条压缩记录

**压缩规范（四段可缺省、可任意组合，但至少要有一段）：**

| 段 | 写什么 |
|---|---|
| `### Done` | 已经做了什么，具体到可验证结果（改了哪个文件、跑到什么状态） |
| `### Next` | 下一步做什么，按依赖排序，用 `- [ ]`，完成即勾选 |
| `### Verify` | 要跑什么测试 / 命令来证明 Done 真的成立 |
| `### Risks` | 有什么坑：试过且走不通的路、容易踩的雷、要避开的事项 |

**每条记录的完整结构：**

```text
1. 时间戳        ISO 8601 带时区，例 2026-10-12T16:20:33+08:00
2. Agent-会话Id  哪个 Agent、哪个会话产生的，例 claude-code / a1b2c3d4
3. 用户原话      用户这一轮的完整原始需求，一字不删、不改写、不概括
4. 本轮压缩      上面的 Done / Next / Verify / Risks 任意组合
```

**落地方式（二选一）：**

- **有 devctx 技能**：AI 调用 `scripts/log_handoff.py <项目根>`，用户原话走 `--user-file`
  （保证一字不删），压缩正文走 `--body-file` 或 `--done/--next/--verify/--risks`；
  Agent / 会话 Id 用 `--agent` / `--session` 显式指定（同会话内复用同一个 session id），
  也可用环境变量 `DEVCTX_AGENT` / `DEVCTX_SESSION_ID`。脚本自动追加记录并重建 `INDEX.md`。
- **没有该技能（自包含降级）**：照 `handoffs/0000-template.md` 手工写一个文件到 `handoffs/`，
  文件名 `<时间戳>-<Agent>-<会话Id>.md`，然后在 `INDEX.md` 补一行。
  时间戳用当前时间，Agent 写你所在工具名，会话 Id 自己生成一个短 id 并在本会话内复用。

### 3.2 每轮顺手：滚动更新 `HANDOFF.md` 与需求文档

把 `handoffs/` 里**最新那条**的结论并进 `HANDOFF.md` 顶部（当前任务 / 进度 / 下一步 / 陷阱 / 改动清单），
让只读 `HANDOFF.md` 的会话也能恢复现场。`HANDOFF.md` 是**当前状态总览**，
`handoffs/` 是**每轮原始流水**，两者不复制内容，只做汇总。
若本轮改了某个需求，同步把结论并进 `docs/<该需求>.md`（文档是需求的长期事实源，比流水活得久）。

### 3.3 结构变动与归档

1. 增删/移动过源码文件时同步更新 `code-index.md`，两条路径任选：
   - **有 devctx 技能的主控环境**：运行其 `scripts/build_index.py <项目根>` 自动重建；
   - **没有该技能的工具（自包含降级）**：按 code-index.md 现有格式手工增量修改对应条目
     （文件、行数、一句话职责），并把头部"生成时间"改为当天；无法可靠统计行数时标注"约"。
2. 架构变化同步改 `architecture.md`；重大决策在 `decisions/` 新增 ADR。
3. `HANDOFF.md` 超过约 120 行时，把「归档线」以下历史移入 `archive/`，活跃区内容只压缩不删除。
4. `handoffs/` 记录数超过约 200 条时，把最旧的搬进 `archive/handoffs/`（活跃窗口不动）。
5. 需求文档已闭环 → `DOCS.md` 里状态改 `stable`；确认废弃 → 归档，别堆在目录里。
6. HANDOFF 陷阱区某个坑**重复出现第二次**，提升到 `lessons.md`（永久教训，不随压缩丢失）。

## 4. 多 Agent 协作约定

多个 Agent / 多个会话同时改一个项目时，靠下面几条避免互相踩：

- **各写各的文件**：每条记录一个文件，文件名带 Agent 与会话 Id，永不覆盖别人的记录。
- **先读索引再动手**：读 `handoffs/INDEX.md` 的「开放 Next」列，看有没有人正在做同一件事；
  要接手别人的活，先读那条记录拿完整上下文，再在自己的记录里写明"接手自 <文件名>"。
- **`HANDOFF.md` 是共享黑板**：它是唯一被所有人滚动更新的文件，冲突时以代码现状为准，
  并把冲突写进自己那条记录的 `Risks`。
- **一个会话一个 Id**：同一会话内复用同一个会话 Id，换会话必须换 Id，否则无法区分是谁写的。
- **一个需求一份文档**：多人改同一需求时都落到 `docs/<该需求>.md` 这一份上，在「需求变更」里
  各自追加，**禁止各建各的文档**——那是特性漂移的主因。
- **新需求先受理**：见 §1.5，判定 EXTEND/CONTINUE/NEW 之后再动手，别急着建文档。

## 5. Token 纪律（硬性）

- **必读预算**：本文件 + `HANDOFF.md` + `handoffs/INDEX.md` 是每次新会话全部固定开销，
  合计约 1000 token 以内；膨胀即瘦身（索引行数靠归档控制）。`docs/DOCS.md` 按需读。
- **分层加载**：L1 入口与 L3 交接必读，L2 规范/索引按需读，源码最后读且只读目标文件。
- **一份内容只存一处**：同一规则不得复制到多个文件或工具私有配置；复用只写路径引用。
- **增量更新**：只改变化的小节，不整体重写未变动文档。
- 工具私有规则文件（CLAUDE.md、.cursor/rules、.trae/rules 等）只允许是指向本目录的指针；
  发现里面长出项目规则，迁回本目录对应文件。
